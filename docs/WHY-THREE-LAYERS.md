# 為什麼漢字需要三層編輯器——從 26 個字母到 10 萬個字

> 這頁寫「為什麼」：為什麼傳統字型編輯器的方法論不能直接套在漢字上，
> 以及我們為什麼要把工作單位從「一個字」降到「部件／筆畫」。
> 不是反對西方工具，是反對**連工作的單位也一起照抄**。

## 0. 一句話

**拉丁字型編輯器的預設單位是「一個字＝一組 contour」；漢字是「幾萬到十幾萬個字，
由少數部件遞迴組成」。單位錯了，再好的鋼筆也救不了。**

## 0.5 我們的價值

不是再做一個字型編輯器，也不是取代 KAGE；是把 KAGE 的**幾何層**補上漢字的**構形層**。

| 層 | 誰做 | 我們的態度 |
| --- | --- | --- |
| 幾何 | KAGE／筆段／輪廓 | **沿用**；它是好素材 |
| 構形 | 部件樹、角色、比例、筆的所有權 | **我們補**；KAGE 的 buhin 沒有 |
| 重用 | component scope、macro、patch | **我們做**；調一次套多字 |
| 驗證 | 筆數、框、比例、replay | **我們做**；不只靠眼睛 |

一句話：**KAGE 讓我們「畫得出字」，我們要讓字「被理解、被重用、被驗證」。**

## 1. 兩個數字

| | 拉丁字母 | 漢字 |
| --- | ---: | ---: |
| 一套字型的基本字形 | 26（大寫）＋26（小寫）＋數字／標點 ≈ **100** | 2 萬（Big5／常用）到 **10 萬＋**（完整 CJK） |
| 一個字一個 contour 調，10 分鐘／字 | ≈ **17 小時**（兩個工作天） | 10 萬字 ≈ **16,667 小時 ≈ 8.3 年**（一人、每天 8 小時、不休息） |
| 同一件事，1 分鐘／字 | ≈ **1.7 小時** | 10 萬字 ≈ **1,667 小時 ≈ 208 個工作天** |

26 個字母，設計師可以一個一個看、一個一個調；那是工藝，不是問題。
**10 萬個字，一個一個調，不是工藝，是算術上不可能。**

## 2. 拉丁模型的三個隱含假設

主流字型工具（FontForge、Glyphs、RoboFont、UFO…）的資料模型，預設了：

1. **字是離散的**：每個字是一個獨立的 outline，字與字之間沒有共享結構。
2. **輪廓是真相**：編輯的單位是 contour／節點；筆畫只是輪廓的視覺結果。
3. **字的數量是有限的**：幾十到幾百個，人可以記住每一個。

這三個假設對拉丁字母幾乎都成立；對漢字，**三個都不成立**。

## 2.5 字母是原子，漢字是二維的詞

拉丁 alphabet 的 letter 單獨沒有語意；語意出現在 word：

```text
c-a-t → cat（一維序列）
```

letter 的內部結構（筆畫、輪廓）是視覺的、任意的；字型只需要存 26 個原子，
排版引擎把 word 排成一維。

漢字不是：

```text
招 = 扌 + 召
```

`扌` 是形符（手），`召` 是聲符（zhào）；它們在二維空間的相對位置，是這個字的語法。
`召` 自己又是 `刀 + 口`。所以漢字本身就是一個**二維的 word**：
部件是詞素／形符／聲符，位置是語法，筆畫是字形。

| | Alphabet | 漢字 |
| --- | --- | --- |
| 原子 | letter（無語意） | component（詞素／形符／聲符） |
| 語意單位 | word（一維序列） | character（二維組合） |
| 內部結構 | 視覺的、任意的 | 語意的、約定的 |
| 字型模型 | 26 個 outline | 10 萬個 outline（結構被丟掉） |
| 編輯單位 | glyph contour | component／stroke |

推論：

- 拉丁字型只存「字母長怎樣」就夠了；word 的語法在字型之外。
- 漢字的 word 在 glyph 裡面；字型卻只存 outline，等於把二維語法壓成一維原子。
- 這不是「漢字比較複雜」，是「**漢字的語意單位與字型單位不一致**」。

把漢字當字母畫，能畫；但畫出來的是一個被壓扁的詞——無法理解、無法重用、無法驗證。

## 3. 直接套用的代價：拿來主義

「拿來主義」不是「不能用別人的工具」；是**把別人的問題設定也一起拿來**：

- 別人問的是「怎麼把這 26 個字母畫好」，所以工具給你 **per-glyph contour editor**。
- 我們問的是「怎麼讓 10 萬個字有一致的部件比例、筆形與筆順」，卻拿了同一個 editor，
  於是工作變成：**逐字、逐筆、逐 contour 調**。
- 結果不是「效率差一點」，是**根本做不完**；做了 2 萬字，還有 8 萬字；
  改了一個部件，2 萬個字要重調。

這不是工具壞，是**單位移錯了**。油畫筆很好，但你不能用它去刷整條街。

## 4. 漢字不是「很多個拉丁字母」

漢字有三個拉丁字母沒有的性質：

1. **遞迴組合**：字 → 部件 → 筆畫；同一个部件出现在几百、几千个字里。
2. **共享與變體**：同一個部件有位置變體（女 vs 女旁、氵 在左／上），
   但變體是**少數**，不是每個字都獨一無二。
3. **結構先於輪廓**：筆順、部件順序、包圍／左右／上下，是字的語法；
   輪廓只是語法的最終投影。

所以漢字的正確問題不是「這個字的 contour 怎麼畫」，
而是「**這個部件在這種角色下的比例／筆形是什麼**，然後套到所有用到它的字」。

## 5. 漢字其實已經有結構——只是工具不讓你用

DFKai-SB（標楷體）本身就是證據：

- **20,914 個 composite**、**242 個筆形基元**、純平移；
- 它不是「每個字畫一次」，是「少數筆形＋組合」。

我們的資料也一樣：

- 21,204 個字、273,714 筆；
- `components.json` 的 56,101 個葉實例，只用到 **1,149 個不同部件**；
- 43 個高頻部件，已覆蓋 **33.5% 的葉實例**；做到 60% 時，約 **3,000 個字**可以完全由已知部件組出；
- 真正「新造」的異體部件，目前只有 **2 個**（`NV-PANG` 女旁、`lei-yu` 雨）。

**結構一直在那裡；是 per-glyph 的編輯器把它藏起來了。**

## 5.5 KAGE／buhin：方向對了，但「部品」不是「部件」

KAGE 已經邁出一步：它不把字當一個 contour，而是把字拆成 **部品（buhin）**，
用引用與筆形基元組合。這是對的——它承認漢字是組合的。

但 KAGE 的誕生背景是**日本戶籍／外字造字**：目標是「快速造出一個可以登記、可以印的字」，
不是「忠實表達這個字的內在結構」。所以它的 `buhin` 是**渲染導向的部品**，
不是**構形導向的部件**：

| | KAGE／buhin | 我們要的部件 |
| --- | --- | --- |
| 目標 | 快速造字、可印 | 結構可理解、可重用、可驗證 |
| 邊界 | 以渲染方便為主 | 以構形序／筆順／部件身分為主 |
| 所有權 | 一筆可能被切給別的部品 | 每筆屬於哪個部件要可追溯 |
| 命名 | 可以是 `&`／`C`／匿名 | 部件要有身分（碼位／角色） |
| 變體 | 視覺變體，語意不一定 | 變體要標 role（左／右／上／下／包圍） |
| 驗證 | 畫得出來 | 筆數、筆順、框、比例、重播 |

後果（在我們的資料裡就看得到）：

- `電` 的 `&`、`學` 的 `&`／`C`：部品是匿名佔位，不是部件。
- `峰` 的 `山` 指向 variant `girt`，不是 standalone 山。
- `邏` 的 `辶` 被拆成「兩點＋折捺」，是為了排版，不是構形。
- `components.json` 的 `strokes` 會把別人的筆吃進來（沇 的 氵 5 筆、蕾 的 艹 10 筆）。

所以我們把 KAGE 放在**幾何層**：它是很好的筆段／輪廓來源，也是「漢字可以組合」的證據；
但**不把它的 buhin 當成構形真相**。構形真相用 `構形序`／IDS／`components.json`＋人工修正的
`DECOMP`，再用 `verify_boxfit.py` 的筆數／框／比例來驗。

一句話：**KAGE 把字拆成部品，是為了快點造字；我們把字拆成部件，是為了讓字被理解、被重用、被驗證。**

## 6. 三層編輯器：把「調整」的作用域降下來

```
字（glyph）
 └─ 部件（component）× n     有順序、有框、有角色
     └─ 筆畫（stroke）× n   中心線＋半寬＋筆型
```

| 層 | 你調什麼 | 作用域 | 一次影響 |
| --- | --- | --- | ---: |
| 字 | 字身框、部件間距、重心 | glyph | 1 字 |
| 部件 | 位置、縮放、比例、部件內筆畫 | component（＋role） | 幾百到幾千個字 |
| 筆畫 | 控制點、寬度剖面、筆型 | stroke／class | 一筆到一整類 |

**核心不是「多一層 UI」，是「作用域」。**
同一個判斷，可以只作用在「這一筆」「這個部件」「這一類筆畫」「整批字」；
調一次影響多少，由 scope 決定——這才是省人力的機制。

## 7. 這不是反西方，是換單位

我們仍然用西方的好東西：

- 向量輪廓、Bézier、OpenType／GSUB、variable fonts 的工程傳統；
- 但**工作的單位**要換：從 `glyph → contour` 換成 `glyph → component → stroke`。

這就像資料庫：你不會因為 SQL 是西方來的，就拒絕用 relational model；
但你也不會把「一張表一個檔案」的 Excel 做法，硬套到 10 億筆資料上。
**工具可以借，問題設定要自己寫。**

## 8. 經濟學：省的不是 bytes，是人的判斷

| 做法 | 調整記錄 | 換一個部件 | 人的動作 |
| --- | --- | --- | --- |
| per-glyph contour | 每個字一組 delta | 重調所有字 | 10 萬次 |
| 三層＋component scope | 一個 component delta | 自動套到所有 occurrence | 幾百次 |

空間也會省（部件只存一次；粗估字形資料 40–60%，緊湊格式可到 70–80%），
但**真正的節省是人的判斷次數**。這個專案的第一指標應該是
「人工調整量」，不是「像素差」——這也是 `PLAN-system.md` 的原則：
**人是瓶頸時，設計要減少人的動作次數。**

## 8.5 幾 MB 的字型，與「系統不懂字形結構」

### 大小：100 套字型不是 100 個檔案，是 100 座山

- 一套完整 CJK 字型常見 **5–20 MB**（Noto Sans CJK 一個 weight 就約 16 MB）。
- 手機裝 100 套：**0.5–2 GB**；還不含可變字型、快取、子集。
- 拉丁字型一套約 **50–200 KB**；100 套 = 5–20 MB，根本不是問題。

同樣是「100 套字型」，拉丁是幾十 MB，漢字是幾 GB。**這不是壓縮率差一點，是數量級差。**

### 系統知識：字型檔只認得 outline

OS／字型堆疊（DirectWrite、CoreText、FreeType）只認得：

```text
codepoint → glyph ID → outline（glyf／CFF）
```

它**不認得**：

```text
glyph → components → strokes
component → role／proportion
stroke → centerline／width／type／order
```

`GSUB` 是**字形替換**，不是**部件組合**；variable font 的軸是全域的（weight／width），
不是「這個部件窄一點、那個部件高一點」。所以漢字的高級功能全部掉到 App 層：

| 功能 | 現在誰在做 | 後果 |
| --- | --- | --- |
| 造字／組字（缺字、合文） | 每個 App 自己寫 | 格式不相容，成果不能共用 |
| 部件檢索、字形比對 | 字典／輸入法各自建索引 | 同一份結構知識重建 N 次 |
| 異體字／缺字替換 | 應用層 hard-code | 換一個 App 就重來 |
| 筆順／筆形教學 | 教育軟體自己拆筆 | 拆法不一致，無法驗證 |
| 字型子集／增量下載 | 各家 build pipeline | 只能按碼位切，不能按部件共用 |
| 依部件／風格替換 | 幾乎沒有 | 只能整字換字型 |

**每一個 App 都在重造同一個輪子；而且造出來的輪子不能給別人用。**

### 缺的那一層

字型檔之上、App 之下，缺一個**結構感知的字形層**：

```text
character → component tree + proportions + strokes + patches
```

它可以是：

- 一個 library（`pinxing`：筆段→SVG）；
- 一個 editor（`pinxing-editor`：三層編輯＋macro）；
- 一個資料格式（`stable-manifest.json`＋`proportions.json`＋`DECOMP`）。

App 透過這一層拿結構，不再各自拆字；同一份比例表、同一份筆畫資料，可以跨 App 共用。
字型檔仍然存在，但它退回到「其中一種輸出／快取」，不再是唯一的知識來源。

| | 字型檔 | 結構層 |
| --- | --- | --- |
| 單位 | glyph | character／component／stroke |
| 內容 | outline | tree＋proportions＋centerline／width |
| 查詢 | codepoint→glyph | 部件、角色、比例、筆順 |
| 壓縮 | 每字一份 outline | 部件共用（同一部件只存一次） |
| 功能 | 排版 | 造字、檢索、教學、驗證 |

**字型檔只會說「這個碼位長這樣」；它不會說「這個字由哪些部件、用什麼比例組成」。
少了這一層，每個 App 都要自己重建一次。**

## 9. 所以我們需要什麼

1. **三層視圖**：字／部件／筆畫同步選取，breadcrumb 下鑽。
2. **scope**：stroke／component／glyph／global；component 要帶 role（左／右／上／下／包圍）。
3. **比例表**：`component + op + slot → (sx, sy, relx, rely)`；調一次，套全部。
4. **macro record/playback**：把人的判斷（before/after、note、decision）錄下來，可重播、可 diff。
5. **delta 層**：核心唯讀；所有編輯存 patch，不寫回 `.bin`。
6. **穩定版／開發版分離**：editor 只讀 stable manifest；dev fixture 不污染穩定輸入。

## 10. 驗收：不要只看 IoU

- **部件覆蓋率**：已做部件覆蓋多少葉實例。
- **重用率**：一個 component delta 平均影響幾個字。
- **人工動作數**：完成一個部件/一批字，人按了幾次、調了幾個值。
- **比例表誤差**：用表預測沒調過的字，predicted_iou／墨跡差。
- **視覺**：最後還是人看；但人只看「部件對不對」，不是「每個 contour 對不對」。

## 11. 一句話

**拉丁字型是「畫 100 個字」；漢字是「定義幾百個部件，讓 10 萬個字自己長出來」。
把 per-glyph 的編輯器套到漢字，不是勤奮，是方向錯了。**

**KAGE 是「部品」，不是「部件」；部品可以拿來畫字，部件才能拿來思考字。**

**字型檔只會說「這個碼位長這樣」；結構層才會說「這個字由哪些部件、用什麼比例組成」。**

**字母是原子，詞才有一維語法；漢字本身就是二維的詞。把漢字當字母畫，等於把詞拆成沒有語法的筆畫。**

**KAGE 讓我們「畫得出字」；我們要讓字「被理解、被重用、被驗證」。**
